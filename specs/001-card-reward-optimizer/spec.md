# Feature Specification: 信用卡消費匯入與通路回饋最佳化

**Feature Branch**: `001-card-reward-optimizer`

**Created**: 2026-10-16

**Status**: Draft

**Input**: User description: "一開始可以匯入自己有的信用卡消費清單(建議大於三個月)並自動初始化建立持卡清單與主要消費通路 × 現有卡清單；後續可輸入通路名稱 → 回傳「現在該用自己已經有的哪張卡 + 需不需要領券」；輸入信用卡健檢 → AI 自動抓取目前常見之信用卡回饋，協助評估是否有更優的通路信用卡來做更換；輸入想辦的信用卡回饋內容 → LLM 回覆是否值得辦卡，是否可替換某通路目前回饋較少的部分，以及有哪些優缺點。"

## Clarifications

### Session 2026-10-16

- Q: 消費清單預計用哪種方式匯入系統？ → A: 表格檔匯入（如 CSV／Excel）＋ 手動輸入；手動輸入採「智慧提問」，由系統逐題引導使用者說明目前的信用卡消費習慣【部分已取代：表格檔匯入已移除，見 2026-10-28「公開版資料入口改成什麼？」】
- Q: 信用卡健檢時，各家信用卡的回饋資訊從哪裡取得？ → A: 系統自動蒐集發卡行公開資訊產生草稿，經管理員確認後才發布（已於 2026-10-28 修訂，見下方 Session）
- Q: 查詢通路時，系統怎麼知道要不要先領券？ → A: 系統蒐集公開的領券資訊產生草稿，經管理員確認後發布；登錄週期為結構化欄位；使用者可在本機標記「已領」（已於 2026-10-28 修訂）
- Q: 逐筆明細的三年保存期限如何起算、到期後如何處理？ → A: 自消費日起算；到期永久刪除逐筆明細，彙整通路月均保留；資料以本機優先存放【部分已取代：保存對象改為彙整表快照、以確認日起算，見 2026-10-28「三年保存期限適用於哪些資料？」；系統不再保存逐筆明細】
- Q: 匯入時超過三年的舊明細是否需告知？自訂通路？ → A: 靜默略過、不需告知；允許自訂通路，預設為 11 項【部分已不適用：「略過超過三年的舊明細」以匯入明細為前提，該入口已移除；自訂通路與預設 11 項仍有效】
- Q: 使用 AI 做分析與建議時，哪些資料可以送給外部 AI 服務？ → A: 只送彙整後的「主要消費通路表格」（各通路月均、卡片與回饋規則），不送逐筆交易明細；可例外加入使用者特別大額的開銷作為小幅個人化項目

### Session 2026-10-28

- Q: 回饋與領券資料要全自動生效，還是需確認？ → A: 半自動：系統蒐集後產出「待確認」草稿，管理員確認才發布；每筆資料保留查證日期與來源；無法判斷的欄位顯示「官網沒有寫」，不硬填
- Q: 領券的登錄週期如何表示？ → A: 登錄週期（每週／每月／每季／活動期間一次）為結構化欄位，「下一次開放日」由程式依規則計算，不由 AI 推測
- Q: 系統整體架構方向？ → A: 參考 japan-card-register 類型的網站：公開網站只提供消費建議資訊，不接收、不上傳使用者個人資料；使用者的消費資料只在自己裝置上處理
- Q: 是否有管理員入口？ → A: 有，但管理員模式只在管理員本機執行、不公開部署。管理員（擁有者）可輸入自己的消費習慣並使用 AI 分析，同時負責確認與發布回饋資料
- Q: 公開版提供什麼？可用 AI 嗎？ → A: 公開版讓使用者填寫消費習慣、在意的通路、想換的信用卡候選、通常刷的金額；可使用在使用者本機執行的 AI，資料不離開裝置
- Q: 公開版瀏覽器內資料是否加密／解鎖？ → A: 不加密、不解鎖，僅在介面告知風險；以「公開版只存非敏感資料、不存末四碼」解決與 Constitution VIII 的關係
- Q: 公開層 API 在哪裡執行？API／SDK 是否必要？ → A: 公開層以瀏覽器內 SDK 計算，回饋資料以公開靜態檔案發布且其他程式可讀取；包成 API／SDK 為必要需求；串 LLM 的操作限近端呼叫；情境推薦為健檢與新卡評估的延伸
- Q: 服務是否包成 API／SDK？存取如何驗證？ → A: 可包成 API／SDK。呼叫進入時先檢查 accessRequirement；需登入者驗證 accessToken，有效後檢查 protectionLevel；允許匿名呼叫；匿名走公開業務邏輯層；已登入者可檢查是否近端呼叫並串接 LLM；任何失敗即拒絕存取
- Q: 三年保存期限適用於哪些資料？ → A: 適用於每次確認保存的彙整表快照，以確認日起算；最新使用中的通路表不受影響
- Q: 公開版資料入口改成什麼？ → A: 使用者取得網站提供的 prompt，自行交給自己選擇的 LLM 分析消費紀錄，再把彙整結果貼回網頁；保留智慧提問；移除表格檔匯入
- Q: 管理員模式的明細與 FR-019 衝突如何處理？ → A: 管理員模式在本機先彙整再送外部 LLM，維持 FR-019
- Q: AI 金鑰如何保管？ → A: 金鑰檔本身加密，管理員登入時以密碼衍生的金鑰解密；管理員於登入後指定金鑰檔位置
- Q: 公開版的本機 AI 如何執行？ → A: 公開版本階段不含 AI，只用程式比對（取代前一題的本機 AI 想法）；AI 僅限管理員模式
- Q: 本機驗證與憑證如何管理？ → A: 本機須有解鎖驗證；憑證須登入管理員帳號後才可調用
- Q: 回饋資料蒐集與發布方式？ → A: 參考 japan-card-labels 的做法（官方頁人工查證、結構化資料、頁面由資料產生、顯示查證日期）
- Q: 幣別？ → A: 以新台幣為主
- Q: 管理員的逐筆消費資料如何進入系統？ → A（2026-11-03）: 管理員自行解析後，直接提供整理好的消費習慣通路表格；系統不解析管理員的原始明細（取代前述「管理員模式在本機先彙整」）
- Q: 資料與技術考量、決策優先順序、成功指標？ → A（2026-11-03，使用者提供）: 資料來源為銀行官網公告加人工核對並標註最後更新日期；決策優先順序為持有卡、當下最高有效回饋（含支付方式疊加）、月上限剩餘空間、是否需登錄／指定通路、使用便利性；卡夾資料僅存在用戶端；未來可接銀行開放 API 或電子支付 App；MVP 成功指標為平均決策時間低於 10 秒、回饋計算準確率在合理範圍、有使用者回報少漏掉回饋的正向案例（見 FR-051、FR-052、SC-013 至 SC-015）
- Q: FR-051 的「支付方式疊加」「指定通路」「使用便利性」如何定義？ → A（2026-11-03，使用者提供）: 選定的支付方式即有對應回饋，不疊加，除非銀行活動頁另外載明；指定通路各卡不同，通路查詢時條列各卡的指定商家，使用者自行輸入欲消費的商家而非用選單；最方便指不需切換權益、在一定金額以下皆給穩定回饋
- Q: 公開模式範圍與角色是否如推論？ → A: 確認：AI 分析僅限管理員；公開模式含通路查詢、健檢（程式比對）、新卡試算；訪客可本機覆寫回饋規則；角色為公開訪客加唯一管理員

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 匯入消費清單並初始化持卡與通路對照表 (Priority: P1)

使用者以兩種方式之一建立初始資料：(a) 取得網站提供的 prompt，連同自己的消費紀錄交給自己選擇的 LLM 分析，再把 LLM 回傳的彙整結果貼回網頁（建議紀錄涵蓋三個月以上）；(b) 回答系統的智慧提問，逐項說明自己目前的信用卡消費習慣（各通路用哪張卡、大約每月消費多少）。系統據此辨識出使用者持有的信用卡與各通路消費，建立「主要消費通路 × 現有卡」對照表，表中每個通路包含：月均估算、現在刷哪張卡、回饋率。

主要消費通路（使用者提供）：

| 通路 | 備註（使用者提供） |
|------|------|
| 🏬 百貨 / GlobalMall | — |
| 🍜 餐飲（含連加 LinePay） | — |
| ✈️ 旅遊訂房 / 機票 | 不定期大額 |
| 🌏 日本 / 國外實體 | 旅遊時集中 |
| ⛽ 加油 | 使用者範例月均 ~$1,200 |
| 📱 海外訂閱（Claude / YT / Apple） | — |
| ☕ 飲料咖啡（連加支付） | — |
| 🚗 叫車 / 交通 | — |
| 🏛️ 政府繳費 / 稅款 | — |
| 悠遊卡自動儲值 | — |
| 無腦刷 | 未歸入上述通路時的一般消費 |

**Why this priority**: 這是所有後續功能（查詢、健檢、辦卡評估）的資料基礎；沒有持卡清單與通路對照表，其他功能都無法運作。單獨完成此功能即可讓使用者看見自己的消費結構。

**Independent Test**: 貼上一份符合格式的測試用彙整結果，確認系統產出持卡清單與通路對照表，且各通路月均金額與貼上內容一致、格式錯誤時被拒絕。

**Acceptance Scenarios**:

1. **Given** 使用者貼上 LLM 回傳的彙整結果，**When** 驗證通過，**Then** 系統先顯示預覽供使用者修改確認，確認後顯示持卡清單，以及每個通路的月均估算、現在刷的卡、回饋率。
2. **Given** 貼上的結果標示涵蓋期間不足三個月，**When** 驗證，**Then** 系統告知資料期間不足建議值，並仍允許使用者選擇繼續或補充資料。
3. **Given** 彙整結果中有無法歸入任何已定義通路的金額，**When** 建立對照表，**Then** 該金額歸入「無腦刷」並可由使用者手動調整通路。
4. **Given** 貼上內容含完整卡號或 CVV，**When** 驗證，**Then** 系統拒絕或遮罩，不保存完整卡號與 CVV；公開模式連末四碼也不保存，僅管理員模式得保留末四碼。
5. **Given** 某通路在分析期間內無消費，**When** 產出對照表，**Then** 該通路月均顯示為 0 或標示無資料，不得虛構金額。
6. **Given** 貼上內容格式不符、數值超出合理範圍或含可疑內容（例如網頁語法），**When** 驗證，**Then** 系統拒絕並指出問題，不寫入資料，也不把內容當網頁語法執行。
7. **Given** 使用者選擇手動輸入而不貼上 LLM 結果，**When** 開始初始化，**Then** 系統依通路逐題提問（目前使用哪張卡、約略月均消費、是否有回饋資訊），並於全部通路詢問完畢後產出持卡清單與通路對照表。
8. **Given** 使用者對某題回答「不知道」或略過，**When** 繼續提問，**Then** 該通路欄位標示為未知，不以預設值填補。
9. **Given** 對照表資料來自使用者自述，**When** 呈現月均估算，**Then** 系統標示該數值為「使用者自述估算」，與由匯入清單計算的數值區分。

### User Story 2 - 查詢通路應使用哪張卡及是否需領券 (Priority: P2)

使用者輸入通路名稱，系統回傳「現在該用自己已持有的哪一張卡」，並說明是否需要先領券才能取得該回饋。

**Why this priority**: 這是使用者日常最常用的決策輔助，直接帶來回饋收益，且僅依賴 P1 建立的資料即可運作。

**Independent Test**: 在已有持卡清單與回饋資料的情況下，輸入各通路名稱，確認回傳的卡片與人工判斷的最佳卡一致，並正確標示是否需領券。

**Acceptance Scenarios**:

1. **Given** 已完成初始化，**When** 使用者輸入「加油」，**Then** 系統回傳持有卡中回饋最佳的一張，並說明其回饋率與是否需要領券。
2. **Given** 使用者輸入的通路名稱未在已知通路中，**When** 查詢，**Then** 系統提示無法辨識並列出可選通路，或建議歸入「無腦刷」對應的卡。
3. **Given** 最佳回饋需先領券，**When** 回傳結果，**Then** 系統明確標示「需領券」及領券條件；若領券資訊不明，標示為未知而非猜測。
4. **Given** 回饋有上限或條件限制，**When** 回傳結果，**Then** 系統一併呈現該限制。

---

### User Story 3 - 信用卡健檢（市場回饋比對） (Priority: P3)

使用者輸入「信用卡健檢」，系統使用已發布的常見信用卡回饋資訊，與使用者的通路消費結構比對，評估是否存在對特定通路更優的信用卡可供更換或新增。公開模式的比對與試算完全在使用者本機由程式完成；AI 說明與解讀僅限管理員模式。

**Why this priority**: 需要依賴 P1 的消費結構與外部回饋資訊，價值高但相依較多，故排在日常查詢之後。

**Independent Test**: 提供固定的一組市場卡片回饋資料與使用者消費結構，確認系統輸出的比較結果與人工試算的回饋差額一致。

**Acceptance Scenarios**:

1. **Given** 已完成初始化且取得市場回饋資訊，**When** 使用者要求健檢，**Then** 系統逐通路列出現行回饋與市場上更優選項，並以依月均消費計算的回饋差額呈現。
2. **Given** 現有卡在所有通路皆為最佳，**When** 健檢，**Then** 系統明確回報無需更換。
3. **Given** 市場回饋資訊取得失敗或未通過驗證，**When** 健檢，**Then** 系統告知資料狀態，不以不完整資料給出確定性結論。資料「過期」不由公開頁面判斷（見 Edge Cases）。
4. **Given** 健檢結果，**When** 呈現回饋差額，**Then** 所有金額由程式計算，AI 僅負責說明與解讀。

---

### User Story 4 - 想辦新卡的評估 (Priority: P4)

使用者輸入想申辦的信用卡回饋內容，系統回覆這張卡是否值得辦、是否可取代某個目前回饋較低的通路，並列出優缺點。公開模式由程式在本機試算並列出條件式優缺點；LLM 的文字評估僅限管理員模式。

**Why this priority**: 屬於決策輔助的延伸情境，依賴 P1 與 P3 的比較邏輯。

**Independent Test**: 輸入一組新卡回饋條件，確認系統指出的可替換通路與回饋差額和人工試算一致，且優缺點內容皆來自輸入的回饋條件。

**Acceptance Scenarios**:

1. **Given** 使用者輸入新卡回饋內容，**When** 評估，**Then** 系統回覆「值得／不值得／視情況」的結論，並說明依據。
2. **Given** 新卡在某通路優於現行卡，**When** 評估，**Then** 系統指出可替換的通路及預估回饋差額。
3. **Given** 新卡含年費、門檻或回饋上限，**When** 評估，**Then** 系統將其納入優缺點，並在試算中計入。
4. **Given** 使用者輸入的回饋內容不完整或有歧義，**When** 評估，**Then** 系統指出缺漏欄位並請使用者補充，而不自行假設。

---

### User Story 5 - 管理員模式：個人消費習慣、AI 分析與回饋資料發布 (Priority: P5)

管理員（擁有者）在自己的本機執行管理員模式，可輸入自己的消費習慣（通路表格與特別大額開銷），使用 AI 分析（健檢說明、新卡評估）；同時負責確認系統蒐集的回饋與領券草稿並發布給公開頁面。

**Why this priority**: 這是擁有者專屬的個人化功能，公開頁面不依賴它即可運作，故排在最後；但回饋資料發布是公開頁面資料的來源，需在 plan 階段確保順序合理。

**Independent Test**: 以管理員身分登入，輸入通路表格並取得 AI 分析；以非管理員身分嘗試進入管理入口與呼叫 AI，確認被拒絕。

**Acceptance Scenarios**:

1. **Given** 管理員在自己的本機執行管理員模式，**When** 輸入個人消費習慣並要求 AI 分析，**Then** 系統僅將彙整後的通路表格送給 AI（FR-019），並回傳分析說明。
2. **Given** 公開網站的訪客，**When** 嘗試尋找管理入口或要求 AI 分析，**Then** 公開網站不存在管理入口與 AI 呼叫途徑，也不會送出任何資料給 AI 服務。
3. **Given** 系統蒐集到新的回饋或領券草稿，**When** 管理員檢視，**Then** 草稿標示來源與查證日期，管理員確認後才發布到公開頁面。
4. **Given** 草稿中某欄位無法判斷，**When** 顯示給管理員，**Then** 該欄位顯示「官網沒有寫」或未知，不被自動填值。

### Edge Cases

- 貼上內容格式錯誤、欄位缺漏時由 FR-025 處理；重複貼上同一份結果時，涵蓋期間與既有快照重疊即提示，由使用者選擇取代、另存或取消，不自動合併，不得重複計入（見 contracts/paste-format.md）。 [INFERRED: 使用者授權助理決定，待使用者確認]
- LLM 彙整結果含退款、分期、跨幣別（外幣）消費時，如何呈現與計算月均？外幣依 Assumptions 以帳單新台幣金額彙整，系統不換算；退款與分期由 prompt 要求 LLM 以淨額、實際入帳金額計入通路總額，月均由程式依總額計算；淨額為負者拒絕。 [INFERRED: 使用者授權助理決定，待使用者確認]
- LLM 回傳的數字有誤或被消費紀錄中的惡意文字誤導時，使用者如何在預覽中發現與修正？預覽與確認見 FR-025；預覽畫面可逐欄編輯，編輯後須重新通過驗證才能確認。 [INFERRED: 使用者授權助理決定，待使用者確認]
- 同一通路有多張持有卡回饋相同或相近時，如何決定推薦順序？依 FR-051 的優先順序；相同時的最終決勝規則 [TBD: 尚未定義]
- 回饋有月上限或累積門檻，且本月已接近上限時，是否改推薦其他卡？系統不追蹤已用額度，也不因接近上限改變推薦；僅依 FR-053 說明每月刷到多少會碰到回饋上限
- 貼上內容或消費紀錄含惡意指令文字（例如商家名稱含給 AI 的指示）時，系統必須當作資料處理，不得被執行。
- 使用者要求系統執行付款、轉帳等金流動作時，系統必須拒絕（僅限唯讀分析）。
- 通路比對失敗的輸入是否回傳給管理者（使用者 2026-11-06 決定要回傳，以便補別名）：此與 FR-032（公開模式不得傳送使用者個人消費資料）及 SC-010（含個人消費資料的對外請求為 0）[CONFLICT]；傳送內容、使用者同意方式、傳送管道（公開頁面為靜態網站，目前沒有後端）[TBD: T092]。決定前不實作任何回傳。
- 通路名稱有多種寫法（簡稱、別名、英文）時的辨識；自訂通路可設定別名見 FR-031，通路與公開資料通路名稱的對應（使用者 2026-11-06 決定）：以公開資料的通路名稱為準（canonical）；比對順序為完整名稱相同、去除括號與「含…」後的核心名稱相同（須唯一對應）、使用者已確認的對應（`canonicalId`）、通路名稱與別名；仍比不到時，只列出名稱部分重疊的候選（核心名稱互相包含，雙方至少 2 個字元）讓使用者確認，確認後才記錄，不自動套用；使用者可自行新增、移除別名。去除領域後綴（例如「加油站」）的清單 [TBD: 由使用者提供，T093]。
- 使用者要求刪除全部資料後，系統不得殘留可還原之資料。
- 已發布的回饋資料很久未經查證時：公開頁面只顯示最後查證日期（FR-026、FR-036），不判斷是否過期，也不顯示「可能過期」之類的提示，健檢照資料計算（使用者 2026-11-04 決定）。管理員模式須在資料超過一定時間未重新查證時提醒管理員；提醒的天數 [TBD: 隨 T059 各銀行更新週期一併決定，T059 完成前不提醒]
- 訪客嘗試繞過驗證直接呼叫 AI 分析功能時，系統必須拒絕。
- 管理員草稿與已發布版本不一致（例如銀行臨時改規則）時，公開頁面以哪個版本為準？（以已發布版本為準，並標示查證日期）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 允許使用者將 LLM 回傳的消費彙整結果（JSON 格式，見 contracts/paste-format.md，各通路金額為涵蓋期間總額）貼入網頁，並建議所涵蓋的消費紀錄為三個月以上。
- **FR-002**: System MUST 於貼上結果的涵蓋期間不足三個月時提示使用者，但允許其繼續。
- **FR-003**: System MUST 從貼上的彙整結果或智慧提問回答建立使用者的持卡清單。
- **FR-004**: System MUST 將消費金額歸類至使用者定義的主要消費通路（見 User Story 1 通路表），無法歸類者歸入「無腦刷」。
- **FR-005**: System MUST 產出「主要消費通路 × 現有卡」對照表，包含：月均估算、現在刷的卡、回饋率；貼上的內容不含回饋率，回饋率由已發布的公開回饋資料查詢，查無資料則標示未知。
- **FR-006**: Users MUST 能手動調整各通路的金額與歸類，以及持卡與回饋率資料。
- **FR-007**: System MUST 提供通路名稱查詢，回傳該通路目前應使用的已持有信用卡，以及是否需要領券。
- **FR-008**: System MUST 於回饋資訊不明（含是否需領券）時標示為未知，不得猜測。
- **FR-009**: System MUST 提供「信用卡健檢」，使用已發布的常見信用卡回饋資訊，並與使用者各通路消費結構比對，評估是否有更優的卡片；比對與回饋差額由程式在使用者本機計算。
- **FR-010**: System MUST 於健檢結果中標示所用回饋資訊的來源與取得時間。
- **FR-011**: System MUST 允許使用者輸入想申辦的信用卡回饋內容，並回覆是否值得辦理、可替換的通路，以及優缺點。
- **FR-012**: System MUST 於新卡評估中將年費、門檻、回饋上限等條件納入試算。
- **FR-013**: System MUST 所有金額與回饋差額由程式計算，不得由 LLM 計算（Constitution X）。
- **FR-014**: AI 助理 MUST 僅進行唯讀分析，不得執行任何金流動作（Constitution IX）。
- **FR-015**: System MUST NOT 儲存完整卡號與 CVV，僅得儲存末四碼（公開模式連末四碼也不保存，見 FR-016）；匯入資料含完整卡號時，須於保存前遮罩（Constitution VII）。
- **FR-016**: System MUST 對敏感欄位進行靜態加密，傳輸一律使用 TLS（Constitution VIII）。 公開模式僅保存非敏感資料（卡名、通路、金額彙整），並定義這些為非敏感欄位，因此不需加密；公開模式 MUST NOT 保存末四碼；管理員模式資料仍適用本條加密要求。
- **FR-017**: System MUST 提供使用者資料匯出與完整刪除功能（Constitution XII）。
- **FR-018**: System MUST 將貼上的內容視為資料，不得將其中文字當作指令或網頁語法執行。
- **FR-019**: System MUST 僅在管理員模式下，且僅將管理員自行整理好的「主要消費通路表格」（各通路月均、現用卡、回饋規則）送給外部 LLM；MUST NOT 送出逐筆交易明細、商家明細、完整卡號；公開模式 MUST NOT 將任何使用者個人資料送給外部 LLM（公開模式本階段不含 AI，見 FR-038）。
- **FR-027**: System MAY 於管理員模式下將使用者特別大額的開銷以彙整項目加入送給 LLM 的通路表格作為個人化；該項目僅含類別與金額，不含商家或逐筆資訊。「特別大額」的門檻由使用者自行設定，預設為 10,000 元；以單筆消費金額判定（單筆達門檻者才納入）。
- **FR-028**: System MUST 在管理員模式首次送出內容給外部 LLM 前，讓管理員檢視實際送出的表格內容並確認；其後若送出內容與已確認的內容相同，MAY 不再要求確認；內容有任何變動時 MUST 再次檢視並確認。 [TBD: 「內容相同」的判定方式與已確認狀態的有效範圍（例如是否跨登入階段）尚未定義]
- **FR-020**: System MUST 支援兩種初始化資料來源：(a) 貼上使用者自行以 LLM 產生的彙整結果；(b) 智慧提問手動輸入。表格檔匯入與 PDF 帳單解析不在本階段範圍。初期支援的銀行為國泰、永豐、富邦、台新四間；各銀行消費紀錄的格式由使用者的 LLM 處理，系統不解析原始帳單。
- **FR-023**: System MUST 提供「智慧提問」手動輸入模式，依通路逐題引導使用者說明目前的消費習慣（使用哪張卡、約略月均消費），並允許略過或回答不知道。
- **FR-024**: System MUST 區分資料來源為「匯入清單計算」或「使用者自述估算」，並在對照表與後續建議中標示。
- **FR-029**: System MUST 對每次使用者確認保存的彙整表快照，以確認日起算保存三年，到期後永久刪除；到期前須通知使用者並提供匯出；目前使用中的最新一份通路表不因快照到期而受影響。使用者要求完整刪除（FR-017）時，所有個人資料（含彙整資料與全部快照）須一併清除。到期刪除的執行時機與機制：[TBD: 留待 plan 階段依設計決定]。
- **FR-030**: （已取消：原條文以匯入表格檔為前提，該入口已移除。）
- **FR-031**: Users MUST 能自訂新增、修改、刪除消費通路；系統預設通路為 User Story 1 所列的 11 項，使用者自訂通路可設定名稱與別名，並同樣適用於對照表、通路查詢與健檢。
- **FR-025**: System MUST 對貼上的內容進行嚴格格式與數值驗證，對格式錯誤、欄位缺漏、數值不合理給出明確錯誤訊息，且不寫入不完整資料；驗證通過後須先預覽，經使用者確認才寫入。
- **FR-021**: System MUST 蒐集發卡行公開的信用卡回饋資訊並產生「待確認」草稿，經管理員確認後才發布到公開網站。蒐集與發布方式參考 japan-card-labels 網站可觀察到的做法：以官方活動頁為來源、人工查證後整理成同一份結構化資料，公開頁面皆由該資料產生，並顯示查證日期與官方頁連結；管理員確認後更新該結構化資料並重新產生公開頁面。 該網站實際作業流程未經作者證實，上述僅為依公開頁面可觀察到的做法；本專案具體作業流程：[TBD: 留待 plan 階段]。使用者可在自己裝置上本機覆寫某筆回饋規則供自己使用，覆寫內容須標示為「使用者修正」且不上傳。 更新頻率依各發卡銀行回饋方案的更新週期而異（各行調整回饋的月份不同），系統須依各銀行各自的週期更新；各銀行具體週期：[TBD: 尚未提供]
- **FR-026**: System MUST 對每筆回饋與領券資料保留來源與查證日期並於公開頁面顯示；無法解析或有疑義的欄位須顯示「官網沒有寫」或未知，不得直接當作確定事實使用。
- **FR-022**: System MUST 蒐集發卡行公開的領券資訊（是否需領券、領券條件、有效期間、登錄週期、名額），經管理員確認後發布；登錄週期（每週／每月／每季／活動期間一次）為結構化欄位，「下一次開放日」由程式依規則與今日日期計算；使用者可在本機將某優惠標記為「已領」；通路查詢（FR-007）須依此顯示「需領券／已領／無需領券／未知」。系統不得代使用者領券。
- **FR-032**: 公開模式 MUST NOT 提供任何將使用者個人消費資料（匯入檔、智慧提問回答、持卡與通路表格）傳送、儲存到伺服器或第三方的功能，含分析追蹤；所有個人資料僅在使用者裝置上處理。
- **FR-033**: System MUST 提供管理員模式，且管理員模式 MUST 僅在管理員自己的本機執行，不隨公開網站部署、不對外提供入口；管理員可輸入個人消費習慣、使用外部 AI 分析、確認與發布回饋資料草稿。本機端 MUST 具備解鎖驗證，管理員功能須登入管理員帳號後才可使用。解鎖驗證僅適用管理員模式，公開模式不設解鎖；管理員 MUST 能使用「忘記密碼」功能重設密碼（使用者 2026-11-03 決定）；由於憑證檔以密碼衍生金鑰加密（FR-034），重設後舊憑證檔無法解密，管理員須重新輸入並加密保存 AI 憑證。 [TBD: 重設時如何確認操作者為管理員本人；管理員模式其他加密資料（FR-016）在重設後是否仍可讀取，取決於其金鑰管理方式（Constitution VIII 尚未決定）]
- **FR-034**: System MUST 確保外部 AI 服務的存取憑證僅保存於管理員本機，不出現在公開網站的任何檔案或請求中；公開網站不具備觸發 AI 呼叫的途徑。憑證檔本身 MUST 加密，管理員登入時以其密碼衍生的金鑰解密後才可調用；憑證檔位置由管理員於登入後指定，系統僅可讀取該單一檔案，且憑證不得出現在日誌或畫面。解密後憑證僅存於記憶體，閒置自動清除；清除時機：[TBD: 留待 plan 階段決定]
- **FR-035**: System MUST 於公開頁面提供通路查詢、健檢（程式比對）與新卡試算，不需登入。
- **FR-036**: System MUST 於公開頁面顯示資料最後查證日期與免責聲明（以發卡行官方公告為準）。
- **FR-037**: 公開模式 MUST 讓使用者填寫：平常的消費習慣、在意或想使用的通路、想更換的信用卡候選、通常刷的金額；這些輸入僅保存在使用者裝置本機。
- **FR-038**: 公開模式本階段 MUST NOT 包含任何 AI（含本機 AI），僅以程式的規則與計算提供查詢、健檢與試算；AI 說明僅限管理員模式。公開版是否於後續階段加入本機 AI：[TBD: 後續階段再評估]
- **FR-039**: System MUST 於公開網站提供版本化的 prompt 並完整顯示，內容要求 LLM 僅輸出固定格式的彙整結果、不重複輸出逐筆明細，金額僅以新台幣表示，且 MUST NOT 索取卡號、姓名等敏感欄位；網站須提醒使用者自行遮蔽敏感資訊，並說明消費紀錄交給所選 LLM 後的處理不受本系統控制。
- **FR-040**: 彙整結果中如含單筆達使用者所設門檻（預設 10,000 元）的大額開銷，prompt MUST 要求 LLM 以獨立項目列出（FR-027 沿用單筆判定）。貼回或接收結果時，System MUST 以程式驗證每個獨立列出的大額項目金額皆達使用者所設門檻，未達者 MUST 拒絕或標示不通過，不得由 LLM 的判斷直接採信；此驗證屬 Validator 的輸入驗證範圍（Constitution XIII）。驗證不通過時的處理方式：[TBD: 拒絕整份或僅標示該項尚未定義]
- **FR-041**: 管理員模式的本機服務 MUST 僅接受本機連線、驗證請求來源，並於每次登入產生一次性令牌，以防止瀏覽器中其他網頁呼叫本機服務。
- **FR-042**: 管理員模式 MUST 接受管理員自行解析其消費明細後整理好的消費習慣通路表格，系統不解析管理員的原始明細；該表格依 FR-028 經管理員檢視確認後才送給外部 LLM，並將 LLM 回傳結果直接帶入，不需人工複製貼上。

- **FR-044**: 每個 API 操作 MUST 於伺服端／程式內宣告 accessRequirement（是否需登入）與 protectionLevel，不得由呼叫端自行宣稱；呼叫進入時 MUST 先檢查 accessRequirement，需登入者驗證 accessToken，有效後再檢查 protectionLevel；允許匿名的操作可不登入呼叫。

- **FR-047**: System MUST 支援依使用者自述的消費情境，或由 LLM 協助列舉的消費情境（公開版由使用者以網站 prompt 自行產生後貼入），結合過去消費習慣與目前持有的信用卡推薦信用卡，亦可從使用者的候選卡中挑選；此為 User Story 3（健檢）與 User Story 4（新卡評估）的延伸，沿用其比對、試算與限制（含 FR-013）。
- **FR-048**: System MUST 將已發布的回饋與領券資料以公開的靜態檔案發布，供公開版 SDK 及其他程式讀取；檔案格式為 JSON，含結構化欄位（回饋率、上限、登錄週期、名額、來源、查證日期）與 schema 版本號；該檔案僅含公開資訊，不含任何使用者個人資料；載入時須經 Validator 驗證 schema。
- **FR-049**: 公開層與管理員層 MUST 套用同一份驗證規則檔（Constitution XIII）：公開層由瀏覽器內執行器執行，管理員層由本機服務執行器執行；兩個執行器 MUST 通過同一組一致性測試案例。輸入驗證兩處皆執行；存取檢查僅在本機服務執行。
- **FR-050**: 公開模式 MUST 在介面明確告知：資料以未加密形式保存於本瀏覽器的儲存空間，使用同一瀏覽器的人可能讀取，清除瀏覽器資料會使其遺失，並提供一鍵清除與匯出備份；匯出的備份檔不加密，匯出前須提示使用者備份檔以明文保存。 備份檔內僅含非敏感資料（使用者 2026-11-03 確認）。
- **FR-051**: 通路查詢與推薦（FR-007、FR-047）決定使用哪張卡時，System MUST 依下列優先順序判斷：(1) 使用者實際持有的卡；(2) 當下最高有效回饋（依使用者選擇的支付方式所對應的回饋；各支付方式的回饋各自獨立，不疊加，僅當官方公告明載可疊加時才依公告疊加）；(3) 月上限（僅依 FR-053 提供「每月最多刷到多少會碰到回饋上限」的說明，不參與排序，不追蹤使用者當月已用額度）；(4) 是否需要登錄、是否為指定通路；(5) 使用便利性（無腦優先），判定為：不需切換權益，且在一定金額以下皆給穩定的回饋者較便利。比較方式為逐項依序比較：前一項能分出高下即決定，平手才比下一項，不加權計分。 [TBD: 第 5 項「一定金額以下」的金額門檻，以及「不需切換權益」「回饋穩定」在資料中如何表示，使用者未指定] [TBD: 支援的支付方式清單；官方公告載明可疊加時，疊加的資料表示方式]- **FR-053**: 對有月回饋上限的回饋規則，System MUST 向使用者說明「每月刷到多少會碰到回饋上限」（該通路或該卡的月消費金額門檻），此金額 MUST 由程式依回饋率與上限計算（Constitution X）；System MUST NOT 要求或追蹤使用者當月已用額度。上限未知或官網未載明時標示為未知。 此處的上限指「回饋金額上限」（使用者 2026-11-03 決定）。[TBD: 計算公式（含分段回饋率）、跨通路共用上限的處理方式，RewardRule 尚未定義]
- **FR-054**: 回饋規則 MUST 以「卡片 × 通路 × 支付方式」各自記錄對應的回饋；支付方式之間的回饋不疊加，僅當官方公告明載可疊加時才記錄疊加並標示來源（使用者 2026-11-03 決定）；查詢時使用者 MUST 能選擇支付方式。
- **FR-055**: 每張卡的回饋規則 MUST 能記錄該卡的指定商家（各卡不同，屬於通路類別之下更細的層級，例如百貨類別下的特定百貨）。通路查詢結果 MUST 條列各卡在該通路類別下的指定商家，讓使用者得知要消費的地方是否有回饋；使用者 MUST 能自行輸入欲消費的商家名稱（自由輸入，不以下拉選單逐項選取，因項目過多影響體驗），系統比對其是否為指定商家；輸入內容視為資料（FR-018）。 [TBD: 商家名稱的比對方式（完全相符、別名、模糊比對）尚未定義；指定商家清單的蒐集沿用 FR-021 的草稿與確認流程，是否另有差異尚未定義]
- **FR-052**: 回饋資料來源 MUST 為銀行官網公告加人工核對，並標註最後更新日期（與 FR-021、FR-026 一致）。

### Key Entities *(include if feature involves data)*

- **信用卡（Card）**: 使用者持有的卡片。關鍵屬性：發卡機構、卡名、末四碼（僅管理員模式保存）、各通路回饋規則。不含完整卡號與 CVV。
- **彙整表快照（SummarySnapshot）**: 使用者每次確認保存的通路彙整表。關鍵屬性：確認日期、涵蓋期間、各通路金額、資料來源標記（LLM 彙整／自述估算）。系統不保存逐筆消費明細。
- **消費習慣自述（HabitEntry）**: 使用者在智慧提問中回答的某通路習慣。關鍵屬性：通路、使用的卡、約略月均消費、資料來源標記（自述估算）。
- **消費通路（Channel）**: 使用者定義的主要消費類別（如加油、餐飲）。關鍵屬性：名稱、別名、月均估算。
- **通路 × 卡對照（ChannelCardMapping）**: 某通路目前使用的卡及其回饋率，關聯 Channel 與 Card。
- **回饋規則（RewardRule）**: 某卡在某通路的回饋內容。關鍵屬性：支付方式、回饋率、回饋金額上限、門檻、指定商家清單、是否需切換權益、是否載明可疊加、是否需領券、領券狀態（需領券／已領／無需領券／未知）、資料來源與取得時間、是否經使用者修正。
- **回饋資料草稿（RewardDraft）**: 系統蒐集後待管理員確認的回饋或領券資料。關鍵屬性：內容、來源、蒐集時間、狀態（待確認／已發布／退回）。
- **管理員（Admin）**: 唯一可確認發布資料、使用 AI 分析的角色。
- **新卡評估（CardEvaluation）**: 使用者輸入的待辦卡回饋內容，及其與現行對照的比較結果。
